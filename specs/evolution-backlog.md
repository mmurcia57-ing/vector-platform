# VECTOR — Evolution Backlog

## 1. Purpose

This is the single governed registry for product evolution outside the current
implementation specification. It records evidence-backed candidates without
authorizing implementation.

## 2. Governance

The backlog does not reopen Steps 0–16, alter CLOSED decisions, or change
`SDD_STATUS`. Promotion requires explicit evaluation, a specification gate,
traceability, and implementation-task decomposition.

## 3. Status Model

Supported statuses: `CANDIDATE`, `EVALUATE`, `APPROVED_FOR_FUTURE_SPEC`,
`REJECTED`, `SUPERSEDED`.

## 4. Promotion Workflow

Evidence / New Need → Evolution Backlog → EVALUATE →
APPROVED_FOR_FUTURE_SPEC → Spec Extension → READY_FOR_IMPLEMENTATION →
Implementation Tasks.

## 5. Relationship to SDD

An item remains outside V1 until a controlled extension is approved. A spec
extension does not itself authorize code; implementation requires its own task,
dependencies, acceptance, and quality gate.

## 8. Anti-Duplication Rule

New needs must first be mapped to EV-001..EV-007. A new EV ID requires evidence
that existing themes cannot represent the need and explicit governance approval.

## 9. Source and Evidence Requirement

Each promotion must record source, authority, provenance, confidence, coverage,
limitations, and unresolved questions. Hypotheses remain hypotheses.

## 10. Scope Guardrail

Backlog entries never become implementation scope by implication. No entry may
be implemented until a specification extension, acceptance criteria,
traceability, task decomposition, and readiness gate have been completed.
